## The problem

Fine-tuning an LLM is easy. Deciding which fine-tune to *deploy* is not.

A model that scores two points higher on quality and needs three times the VRAM
and twice the latency is worse for almost every real deployment. But "which model
should we ship?" is usually answered by whoever squints at a spreadsheet last,
and the reasoning evaporates the moment they leave.

ForgeML makes that decision **measured, automated and explainable**:

- train several arms through **one code path**, so the comparison is about
  methods rather than about whose script was better;
- measure **four axes** — quality, latency, memory, cost — through one evaluator;
- apply an **explicit policy**: hard constraints first, then a weighted utility;
- **register the winner automatically**, with its own justification attached.

The champion is frequently *not* the highest-scoring model. That is the point.

## Quickstart

```bash
git clone https://github.com/kkrishna-labs/forgeML && cd forgeML
```

```bash
uv venv .venv --python 3.12 && uv pip install -e ".[tracking,api,dev]"
```

Run the smoke pipeline first. It trains a tiny random-init model in about two
minutes on CPU and catches every wiring bug before you spend a GPU hour:

```bash
forgeml data prepare --config configs/smoke.yaml && forgeml train --config configs/smoke.yaml --no-mlflow
```

Then the real thing (GPU recommended):

```bash
forgeml data prepare --config configs/base.yaml
```

```bash
forgeml train --config configs/lora.yaml
```

```bash
forgeml select --output reports/selection.json
```

Serve it:

```bash
forgeml serve --model models:/forgeml_champion@champion
```

## API

```
GET  /health    liveness — cheap enough for a 1s probe
GET  /model     which model is serving, and how it scored
POST /predict   generate
GET  /metrics   in-process request counters
```

```bash
curl -X POST localhost:8000/predict -H 'Content-Type: application/json' -d '{"prompt":"Explain overfitting in machine learning."}'
```

```json
{
  "model": "forgeml-champion",
  "prediction": "Overfitting happens when a model memorises...",
  "latency_ms": 183.4,
  "prompt_tokens": 42,
  "completion_tokens": 96,
  "finish_reason": "stop"
}
```

`/model` is the endpoint that makes this an ML service rather than a web service.
An API that will not tell you which model version answered cannot be operated —
you cannot correlate a bad answer with a bad deployment.

## Reproducibility

Every run records what it would take to reproduce it:

- the **fully resolved config** as a YAML artifact, not the override you launched;
- a **dataset content hash** over every example, so the data claim is verifiable;
- the **git commit** (with a `-dirty` marker) as a tag;
- library versions, GPU model and driver in `env.*` tags;
- the seed, applied to Python, NumPy and torch.

```bash
forgeml train --config configs/lora.yaml --set training.learning_rate=1e-4
```

## Testing

```bash
pytest
```

The suite is offline and torch-free by design — no GPU, no downloads, no network.
CI additionally asserts that importing the decision layer does not pull in
`torch`, so the CPU-only guarantee cannot rot.

## Limitations

Stated here rather than discovered later:

- **Quality metrics are n-gram overlap** against a single reference. A correct
  paraphrase scores badly; a fluent falsehood scores well. Perplexity is reported
  alongside because it fails differently.
- **Latency and memory are hardware-specific.** They rank models on identical
  hardware; they are not portable numbers.
- **Cost is a derived estimate** from measured throughput and a stated hourly
  rate. It ignores cold starts, idle time and autoscaling.
- **Small models hallucinate.** Nothing this serves should be trusted without
  verification.
- **Databricks Free Edition has no GPU serving**, so the serving path is
  demonstrated through the registry plus a Hugging Face Space rather than a live
  Databricks endpoint.

## Future work

- a second seed per arm, to report run-to-run variance instead of assuming it away
- LLM-as-judge scoring as an *optional* third quality signal
- INT8 and GPTQ arms alongside NF4, to widen the quantization axis
- batch-size sweeps feeding a proper throughput/latency knee analysis
